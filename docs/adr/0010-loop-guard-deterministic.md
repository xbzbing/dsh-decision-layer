# ADR-0010：防循环确定性、不走后端

- 状态：Accepted（2026-10-26）
- 相关：`service/loop-guard.mjs`、`service/dsh.mjs` 的 `ctx.tools.guard`、ADR-0006

## Context

agent 卡在「同一个工具调用反复重试」是常见故障，靠模型自我察觉不可靠——循环时模型自己往往正是循环的一部分。

备选：交给裁决模型判断（故障时仍要发请求；而「重复调用是否合理」需要看历史，正是最容易自我合理化的地方）；纯本地计数（可能误判合法的重复调用）。

## Decision

- 纯本地计数，判定依据是**调用指纹**：`sha256(工具名 + \0 + 参数 JSON)`，参数序列化截断到 16KB。
- 同一会话内，指纹**连续**相同就把计数 +1，任何不同调用重置为 1；计数 `>= threshold`（默认 3）即拒绝该次调用——也就是连续第 3 次相同调用被挡。
- 不走后端、不看内容语义，因此后端故障时依然工作，也不产生额外请求与延迟。
- 计数按会话隔离，最多保留 1024 个会话的计数状态（超出后淘汰最早的一条），避免长跑进程无界增长。
- 不参与四个决策点的功能开关（它没有开关），但**受会话总开关约束**：用户主动关掉自动介入时，防循环也一并暂停（与门控一致）。
- 阈值不进配置（ADR-0006）：它是保护机制而非待标定的启发式。
- 与门控共用 `tools.guard` 通道：两者都只能拒绝、不能放行；注册顺序是先防循环、后门控。

## Consequences

- 行为完全可预测：同一个调用连续出现第 3 次必被拒，与模型无关。
- 代价一：合法的重复（例如对同一路径反复 `read` 期望内容变化）会被误判——指纹含参数，所以「参数完全一样」才算重复，粒度已经是最窄的了，但这类场景本身没有更好的判据。
- 代价二：**它不写日志、不计指标**，拒绝只体现为工具错误。排查「为什么这个命令被拦」时，用户看到的是错误信息而不是一条决策记录；要定位是门控还是防循环，只能看错误文案里的 `Identical tool call repeated` 与门控的 `Dangerous call rejected`。
- 「受会话总开关约束」是有意的：总开关的语义是「本会话不要自动介入」，防循环属于自动介入，不该例外；但它与门控不同，没有独立开关，所以无法单独关掉。
