# ADR-0007：工具收窄的三重保护

- 状态：Accepted（2026-10-26）
- 相关：`service/narrowing.mjs`、`service/dsh.mjs` 的 `installNarrowingHook`、ADR-0002、ADR-0006

## Context

收窄在每个回合开始时按任务相关性删掉用不上的工具，收益是缩小模型的选择面，风险是**删掉本轮真正要用的工具**——而且失败往往要几步之后才显现，很难归因。

备选：不做保护（一次误删就是事故）；只记录不生效（等于没有这个功能）；让模型自己声明需要哪些工具（多一轮往返，且模型未必知道）。

## Decision

- **A. 核心工具永不判定**：读写/编辑/Shell/检索/待办，以及 agent 元能力（问用户、目标、技能、交付、图片、后台作业、协作、子代理）始终保留，不下发裁决请求。名字命中 `keepPrefixes` 的同样保留——默认 `mcp__openviking`、`team_task_`，因为记忆/协作类工具「常驻、按需触发」，字面相关性极低，逐工具判定会稳定误删。
- **B. 候选超限降级**：参与判定的可选工具数 > `maxCandidates`（默认 20）时只观察、不生效。上限同时受协议硬限（单请求 ≤64 题）夹住。
- **C. 保留过少视为不可信**：`keep.length < minKeep`（5）时整条判定作废，不施加任何限制。
- 只在宿主已允许的集合内取交集，**绝不扩权**；`observe` 只记录，`enforce` 才限制，且限制在下一回合前解除。
- 分批按后端上下文容量自适应（`batchMode`）：`auto` 先整批，遇上下文超限则降级为「每工具一次请求」并记住；也可显式指定 `single` / `split`。拆分中失败的工具保守保留。

## Consequences

- 最坏情况是「收窄没生效」，而不是「工具被删光」——失败方向安全。
- 代价：核心工具表与 keep-prefix 是硬编码默认值，新增工具若不登记就可能被误判（当前默认集已覆盖 DSH 主要能力，keep-prefix 可在配置里追加）。
- 三重保护的阈值（20 / 5）不暴露成配置：它们是保护机制而非待调优参数。`maxCandidates` 可配属于「要不要更激进地收窄」这一层，语义不同。
- 小上下文后端（本地 `tev1`，约 2050 token 单请求上限）依赖拆分；`auto` 让同一份配置在云端与本地都能用，代价是首次会遇到一次上下文超限错误并记入日志。
