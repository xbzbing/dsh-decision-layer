# ADR-0003：危险门控只在高置信 `deny` 时拦截

- 状态：Accepted（2026-10-26）
- 相关：`service/danger-gate.mjs`、`service/dsh.mjs`、ADR-0004、ADR-0006

## Context

门控要在破坏性工具调用前拦一刀，但它自己也是故障源：误拦会让正常命令失败，而它盯的恰恰是 `bash`、`write`、`edit` 这类主力工具。

早期实现有第三档「转交宿主审批」（`ask`）。实测它会在 UI 上被渲染成「用户拒绝了该操作」，把**模型的判断伪装成人的决定**——这是语义污染，不能接受。同时门控一旦走宿主审批，用户还会被无意义地打断。

备选：任何置信度都拦（低置信 = 大量误拦）；保留 `ask` 三档（语义无法与宿主审批区分）；只记日志不拦截（安全网失效）。

## Decision

- 只有 `choice === 'deny'` **且** `confidence >= minConfidence`（默认 0.6，可配，见 ADR-0006）才拦截：以 `kind: 'deny'` 返回，经 `tools.guard` 单调生效，不经过宿主的审批策略。
- 其余一律不介入，并记 `action: 'pass'`：高置信 `allow`、任何 `ask`、低置信 `deny`、响应不合法、后端失败。
- 门控**不再发出** `ask`，因此不会路由到宿主审批，也不会被误渲染成「用户拒绝」。
- 拦截是单调的：`tools.guard` 只能拒绝，后续 hook 不能重新放行。
- 分类先于裁决：只有命中危险工具名 + 命令/路径正则的调用才发请求（`rm -rf`、`git push -f`、`drop/truncate`、`kubectl delete`、prod 写操作、`.env` / `etc` 路径等）。
- 发送的 state 是脱敏摘要：工具名 + 命令 + 路径，密钥类字段替换为 `[redacted]`，**不含文件内容**。

## Consequences

- 门控的失败方向是「放行」，与「安全工具」的直觉相反，但符合「不因裁决故障阻断 agent」（ADR-0004）。
- 三档里的 `ask` 只作为模型输出存在、无宿主副作用，因此「模型建议 ask」当前等价于放行，只在日志可见——这是刻意的取舍，不是遗漏。
- 交互只减不增：门控从不授予新权限，也不替宿主放行。
- 若将来要恢复「转交审批」，必须先解决两件事：UI 上区分「模型建议」与「人的决定」，以及审批留痕。否则会重蹈被误读为「用户拒绝」的覆辙。
