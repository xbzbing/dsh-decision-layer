# ADR-0009：完成核对：确定性提取 + 三态判定

- 状态：Accepted（2026-10-26）
- 相关：`service/task-completion.mjs`、`service/dsh.mjs` 的 `installCompletion`、ADR-0008

## Context

「用户列了三件事，agent 是否都做了」是自检抓不住的一类遗漏：自检看回答质量，不看任务清单。难点有两个：

1. **条件从哪来**：让模型总结条件会引入一次额外裁决，且条件可能被模型改写；
2. **凭什么判定完成**：看 agent 的回复会把「自称完成」当证据；只看工具证据又会漏掉不需要工具的条件。

备选（提取）：模型总结（不可控、可能臆测隐含期望）；只认显式结构化形式（覆盖窄，但不臆测用户意图）。

## Decision

- **提取是确定性的、不调模型**：只识别结构化形式——编号列表、项目符号列表、单行顿号/逗号分隔的多命令。不推断隐含期望。
- 条件数 < `minConditions`（默认 2），或本回合没有任何工具证据时，直接跳过、不发请求。
- 每个条件一题 `choice`，三态：`satisfied` / `unsatisfied` / `insufficient_evidence`。
- state 同时给「工具证据（工具名 + ok/error）」与「最终回复」，并**明示**工具证据才是判据、回复自述不算证据；证据不足时选 `insufficient_evidence`。
- 补完需要 `unsatisfied` 的置信度 ≥ `minConfidence`（默认 0.4）；`insufficient_evidence` **不**触发补完。
- 与自检并存、指标分列；默认 `observe`。补完只开启一个补充步骤，**不改写**已经提交的回复。

## Consequences

- 覆盖有意偏窄：散文式需求（「顺手把文档也改一下」）不会被识别，因此不会误报未完成。
- 代价：用户以为「我列了条件」但格式不规范（如「第一，…；第二，…」）时不会触发；识别的是形式，不是语义。
- 只看工具证据会漏掉「无需工具即完成」的条件（例如纯回答类），这类倾向于判 `insufficient_evidence`，不触发补完——失败方向安全。
- 多个 `unsatisfied` 时取**其中最小置信度**作为整体置信度：任一条件不确定就整体不补完。另有一条反向规则——某个条件的低置信 `satisfied` 不会压低另一个条件的高置信 `unsatisfied`。
